# 기술 의사결정 기록

면접에서 "왜 이 기술을 골랐나"에 답할 수 있도록, 결정마다 배경·대안·결론을 남깁니다.

## 1. 플랫폼: 웹앱(PWA) 먼저, 앱스토어는 나중에

- **배경**: 혼자 개발·운영하며 아이폰·안드로이드 사용자 모두에게 빨리 배포하고, 면접관에게 링크로 바로 보여주고 싶음
- **대안**: 네이티브 앱(React Native·Expo), 웹 코드를 앱으로 포장(Capacitor)
- **결론**: PWA로 시작하고, 앱스토어가 필요해지면 같은 코드를 Capacitor로 포장
- **근거**
  - iOS 16.4 이상은 홈 화면에 추가한 웹앱에서 웹 푸시를 받을 수 있음 (브라우저 탭에서는 불가, 권한 요청은 사용자 동작 필요)
  - 앱스토어는 등록비(Google Play 1회 25달러, Apple 연 99달러)와 심사, 신규 개인 Google Play 계정의 비공개 테스트(테스터 12명, 14일) 조건이 있음
- **주의**: iOS PWA는 오래 열지 않으면 기기 저장 데이터가 지워질 수 있음 → 모든 기록을 서버 DB에 저장

## 2. 백엔드: Spring Boot로 직접 구현

- **대안**: NestJS(TypeScript 통일), 관리형 백엔드(Supabase 등)
- **결론**: Java 21 + Spring Boot
- **근거**: 국내 백엔드 채용에서 널리 쓰이는 스택이고, 인증·권한·트랜잭션·DB 설계를 직접 구현해 백엔드 역량을 보여주기 위함. 관리형 백엔드는 빠르지만 이 부분이 가려짐

## 3. 저장소: 하나의 저장소에 frontend / backend

- **결론**: 단일 저장소
- **근거**: 혼자 관리하므로 기능 하나를 프론트·백엔드 함께 한 커밋·PR로 묶어 추적하기 쉬움. CI는 경로별로 나눠 실행

## 4. 인증: JWT (Spring Security OAuth2 Resource Server)

- **대안**: 세션 + 쿠키, 외부 라이브러리(jjwt)
- **결론**: 서버가 HS256으로 서명한 JWT를 발급하고, Spring Security의 Resource Server로 검증
- **근거**: 웹과 이후 앱(Capacitor)이 같은 방식으로 인증. 검증 로직을 직접 짜지 않고 Spring Security 표준 구성을 사용해 실수를 줄임
- **보완 (2단계)**: 리프레시 토큰과 로그아웃 추가 → 8번

## 5. DB 스키마: Flyway 마이그레이션 + JPA `validate`

- **결론**: 테이블은 Flyway SQL로만 바꾸고, JPA는 엔티티와 스키마가 맞는지만 검사
- **근거**: 운영 DB에서 JPA 자동 DDL은 의도치 않은 변경 위험. 스키마 변경 이력이 코드 리뷰 대상이 됨

## 6. 테스트: Testcontainers로 실제 PostgreSQL

- **대안**: H2 메모리 DB
- **결론**: 통합 테스트는 Docker로 실제 PostgreSQL을 띄워 실행
- **근거**: H2는 PostgreSQL과 문법·타입 차이가 있어, Flyway SQL과 쿼리를 운영과 같은 조건에서 검증하기 위함

## 7. 주요 이벤트: 저장하지 않고 계산

- **결론**: 의료 일정·치료 정보·유통기한 임박·재구매 필요는 원본 데이터에서 매번 계산
- **근거**: 먹이 남은 양이나 다음 예정일이 바뀔 때마다 이벤트 테이블을 같이 고치면 불일치가 생기기 쉬움. 데이터 양이 적은 개인 서비스라 계산 비용이 작음. 알림 발송 단계(4단계)에서 발송 이력만 별도로 저장

## 8. 리프레시 토큰: 해시 저장 + 사용할 때마다 교체(회전)

- **배경**: 액세스 토큰(JWT)은 서버에서 취소할 수 없으므로 수명을 30분으로 줄이고, 다시 로그인하지 않도록 리프레시 토큰(14일)을 둠
- **대안**: 리프레시 토큰도 JWT로 발급, 긴 수명의 액세스 토큰 하나만 사용
- **결론**: 무작위 문자열을 발급하고 DB에는 SHA-256 해시만 저장. 쓸 때마다 새 토큰으로 바꾸고, 이미 쓴 토큰이 다시 오면 그 사용자의 토큰을 모두 무효화
- **근거**: DB에 원문이 없어 유출돼도 재사용 불가. 탈취된 토큰이 정상 사용자와 번갈아 쓰이면 재사용으로 드러남. 로그아웃 시 서버에서 실제로 무효화 가능
- **구현 메모**: 재사용 감지 후 예외를 던져도 무효화가 저장되도록 `@Transactional(noRollbackFor = BusinessException.class)` 사용

## 9. 소셜 로그인: 서버가 인가 코드를 교환, 같은 이메일 계정과 자동 연결하지 않음

- **결론**
  - 브라우저는 인가 코드만 받아 서버로 보내고, 제공자 토큰 교환과 사용자 정보 조회는 서버가 함 (시크릿을 브라우저에 두지 않기 위해)
  - 콜백 주소는 서버 허용 목록과 일치해야 함, 프론트엔드는 `state` 값으로 요청 위조를 확인
  - 처음 들어온 소셜 계정은 새 사용자로 가입하고, 같은 이메일의 기존 계정과 자동으로 합치지 않음
- **근거**: 이메일만 같다는 이유로 합치면, 제공자 쪽 이메일 확인이 허술할 때 남의 계정에 들어갈 수 있음. 계정 연결은 로그인한 상태에서 직접 하는 기능으로 따로 만들 예정
- **트레이드오프**: 같은 사람이 이메일 가입과 소셜 로그인을 따로 하면 계정이 둘이 됨

## 10. 건강 기록: 날짜별 한 건 + 덮어쓰기, 빠른 기록은 부분 반영

- **결론**: (반려동물, 날짜)에 유일 제약. 상세 화면 저장(PUT)은 전체 덮어쓰기, 빠른 기록(batch)은 보낸 값만 반영
- **근거**: 하루 상태를 여러 건으로 쌓으면 달력·그래프에서 어떤 값을 쓸지 모호해짐. 빠른 기록이 상세 화면에서 입력한 체중·메모를 지우면 안 됨
- **검증**: 일괄 기록은 한 트랜잭션으로 처리해 남의 반려동물이 섞이면 아무것도 저장하지 않음 (테스트로 확인)
